## 摘要

本 ADR 约定：**支持** Session 在异常或中断后的恢复，但仅承诺 **阶段化、边界化的有限恢复**，不追求任意中断点的无损续跑。恢复锚点落在用户轮次、**一轮 completion 的 `Done`**（其后为工具授权与执行）、**工具执行结束**（`ToolCallFinished`，与既有 `ToolResult` 为同一语义、实现向该命名统一）等离散节点；**过程类事件**（授权提示、授权结果、`**ToolCallStarted`** 等）用于实时交互与审计，**不驱动** core 仅从 **transcript**（在当前实现中由 `SessionEvent::UserMessage` 与 `SessionEvent::AgentEvent` 承载的 `AgentRunResponseMessage` 序列）重建发给模型的上下文。

**Transcript** 在实现上记录全量 `SessionEvent`（其中 `SessionEventKind::AgentEvent` 携带 `AgentRunResponseMessage`）；**历史只读 UI** 对协议中的授权类事件过滤渲染；**实时 stream** 照常处理授权。**业务闭环**以「执行结束事件是否落盘」为主要依据时，可采用「无结束事件则实时路径上重授权并重执行」的简化策略，与保守 at-most-once 张力须由产品与工具幂等策略吸收。

另约定一 **窄场景**：在已见若干 `AssistantToolCallRequest` 但未见 `RequestsDone`（及可能未见助手文本结束标记）时，可 **合成 `RequestsDone`**、**不重跑 completion**，以明确产品假设为代价（详见 §5.2）。

---

## 1. 背景与问题

典型 Session 一轮包含：接收用户输入（或恢复入口）→ 驱动 Agent 推理与工具执行 → 持久化事件 → 进入下一轮。任一步都可能因崩溃、断连、上游错误或用户中断而停止。**真正要回答的不是「会不会断」，而是「断在何处时，系统对外承诺什么恢复语义」。**

据此需对齐：

- 是否承诺**任意点**无损继续？（本 ADR：**否**）
- **工具批次**在中间态与 **已闭合**态下，恢复前提有何不同？
- **有副作用的工具**在「结果不明」时如何对待？
- **状态真理**：谁在叙事上、谁在流程上拥有权威？**Transcript（SessionEvent 序列）** 与 UI 分工如何？

若不与上，任意扩大恢复面会以组合爆炸与外部副作用风险反噬可靠性。

---

## 2. 分析：阶段、事件与恢复

以下「推论」指对**恢复语义与产品设计**的含义，不作形式逻辑上的强因果表述。

### 2.1 推理尚未收敛

推理结果若尚未稳定为可消费输出，用 **用户问题 + 历史** 重跑一轮通常可行；一般尚无对外承诺的副作用，代价与风险相对可控。

### 2.2 文本流中间态

若无 **prefill**（或等价能力），很难承诺在「半条生成」上**同轨迹**续写；续写依赖模型侧不可见状态，不仅依赖已展示文本。

### 2.3 工具请求：开放批次 vs 已闭合批次

工具阶段有两类信号需区分：

- **若干条** `AssistantToolCallRequest`
- **一次**「本批请求已全部给出」——下文记为 `**RequestsDone`**（与实现中名称可对应）


| 情形                    | 含义                        | 对恢复的影响                                                     |
| --------------------- | ------------------------- | ---------------------------------------------------------- |
| **未见 `RequestsDone`** | 已观测请求可能只是**真子集**，仍可能有后续请求 | 一般**不具备**「已确认、可授权执行的全批次」；稳妥路径包括重跑 completion 或接受不完整批次的产品风险 |
| **已见 `RequestsDone`** | 本助手轮次工具清单与顺序**冻结**        | 可作为 **Level 2 流程恢复**的稳定锚点；从未闭环的 `call_id` 起继续授权与执行         |


**产品窄场景（与上表一般规则并存）**：若 **transcript** 中已有多条 `AssistantToolCallRequest`，但 `**RequestsDone` 与（若协议需要的）助手文本结束标记** 因落盘/投递丢失而未出现，可 **不重跑 completion**、**补发合成 `RequestsDone`**（必要时一并补文本阶段结束事件），并 **假定 transcript 中的请求即为本轮全部请求**。该假设若不成立，仍有 **漏执行**风险；**无任一工具请求、仅半截文本** 时不适用此捷径。

### 2.4 授权与执行之间的过程信号

以下事件在实时 **`run` / `resume`** 中可能出现，且 **transcript** 可全量记录；**对同一 `call_id` 多次出现**不改变 core **replay** 推导出的、供模型继续推理的上下文（闭环由 **执行结束事件** 等决定，见 §5.5、§5.6）：

- `AssistantToolCallAuthorizationRequired`
- `ToolCallAuthorization`
- `ToolCallStarted`

**历史只读 UI**（仅从 transcript 渲染、无活动 Agent）应对 **前两类授权相关事件** 过滤，避免误造授权交互；执行阶段过程信号的展示策略可由产品另定。实时侧若希望减少重复授权打扰，可用 **业务缓存、自动同意** 等体验层手段。**重复工具执行**（副作用）与 **transcript 里多几条过程事件** 不是同一风险维度（见 §2.5、§5.4）。

### 2.5 工具执行与副作用

外部工具**不天然幂等**；在「结果不明」时自动重放可能造成重复扣费、重复写入等。当前选择采用**简化闭环策略**（以执行结束事件落盘为准、否则实时路径重跑），并由产品与 **工具/远端幂等设计** 共同承担其重复执行风险。

## 3. 备选方向（摘要）


| 方向         | 要点                     | 结论                 |
| ---------- | ---------------------- | ------------------ |
| 不做恢复       | 实现简单                   | 可用性与长链路体验差         |
| 任意点全量恢复    | 能力看起来最强                | 状态爆炸、跨组件一致性与副作用不可控 |
| **有限边界恢复** | 离散 checkpoint + 明确事件分层 | **采纳**：与本 ADR 一致   |


---

## 4. 决策结论

1. **恢复定位**：**可重放 + 可继续**，不是 **同轨迹续跑**；不承诺 token 级中间态无损接续。
2. **Checkpoint**：落在用户轮次、`**RequestsDone` 之后已闭合的**工具批次、授权/执行阶段边界、**工具执行结束** 等处；**未闭合**的工具请求缓冲**通常**不构成稳定恢复锚点，**例外**见 §2.3 窄场景。
3. **工具安全策略（拍板）**：采用 **简化策略优先**——以执行结束事件是否可靠落盘作为闭环依据；无结束事件则在实时路径 **重授权并重执行**。该策略 **接受重复执行风险**（例如远端已执行但结束事件丢失时），由产品侧风险承受与工具/远端幂等设计兜底。
4. **转录与 UI 分层**
  - **Transcript**：持久化与 **`run` / `resume`** stream **一致的全序事件**（含授权类等）。  
  - **历史只读 UI**：对 `**AssistantToolCallAuthorizationRequired`、`ToolCallAuthorization`** **过滤**（不弹授权、不调用提交授权 API）。  
  - **实时 stream**：**完整**处理授权与后续执行阶段事件。  
   **业务是否闭环**以 **执行结束事件**（`ToolCallFinished`）是否可靠落盘为主要判据之一；当前采用**简化策略**：无结束事件则在实时路径 **重授权并重执行**，并接受其潜在重复执行风险。
5. **工具执行阶段事件（正式）**：`AgentRunResponseMessage` **必须**包含 `**ToolCallStarted { call_id }`**，在实时 **`run` / `resume`** stream 中于单次工具执行开始前发出（挂点由实现固定并文档化；用户 **拒绝** 授权时不发送）。`**ToolResult`** **重命名为** `**ToolCallFinished`**（载荷约定不变，如 `call_id` + `content`）；与 `**ToolCallStarted**` 成对表征执行区间。细则见 §5.6。

## 5. 规范细则

### 5.1 恢复能力分层（概念）

- **Level 1**：上下文恢复（会话与用户/助手消息等）。  
- **Level 2**：流程恢复（待授权、待执行、待下一轮 completion）。  
- **Level 3**：副作用恢复（仅当工具/协议显式允许安全重试时）。

### 5.2 工具批次与 `RequestsDone`

- **未闭合**：无 `RequestsDone` 时，不把已观测请求默认视为已提交全批次；除非你方显式接受不完整批次风险，或采用 **§2.3** 的合成闭合窄场景。  
- **已闭合**：出现 `RequestsDone` 后，`[若干 AssistantToolCallRequest …, RequestsDone]` 视为**本助手轮次已提交批次**，可从批次内未完成项继续。  
- **合成 `RequestsDone`**（窄场景）：条件、动作、假设与反例见 **§2.3**；合成事件建议可在元数据中标记可追溯来源。

**测试维度**：须区分中断发生在「最后一条 request 与 `RequestsDone` 之间」与「`RequestsDone` 之后」；并对合成策略做正例与 **零 tool request + 半截文本** 的负例。

### 5.3 转录存储与 UI 消费分层

- **类型与 stream**：当前实现以 `SessionEvent` 作为统一持久化与流式事件形状，其中 `SessionEventKind::UserMessage` 与 `SessionEventKind::AgentEvent` 承载用户句与 `AgentRunResponseMessage`；差异在 **消费者职责**。  
- **Transcript vs 叙事 UI**：授权类事件存在于 **transcript**；**面向用户的只读叙事**可不消费它们——这是 **消费分层**，不必拆第二套事件类型。  
- **实时 Session/Agent 协作**：Session 负责轮次与状态门控，Agent 负责执行；授权 UI 与 `reply_tool_authorization` 行为不变。**transcript** 中的历史 `ToolCallAuthorization` **不**自动豁免新一轮实时授权（除非业务显式缓存自动同意）。  
- **未闭环歧义**：transcript 单独难以区分「从未授权 / 已授权未执行 / 已执行未落盘」；待办推演仍依 **执行结束事件**、批次闭合规则与 §5.4；仅有 `**ToolCallStarted` 无结束事件** 视为未闭环歧义。合规若需与界面分离，可走审计导出等，不改变「历史 UI 过滤授权」策略。

**职责小结**


| 消费者                 | 授权类两事件   | 备注          |
| ------------------- | -------- | ----------- |
| Transcript 持久化      | 记录       | 全量 fidelity |
| 历史只读 UI             | 不消费 / 过滤 | 不误造授权交互     |
| 实时 `run` / `resume` | 处理       | 人机环路        |


### 5.4 工具调用安全策略

- **当前选择**：采用 **简化策略**。以 **执行结束事件** 是否已可靠落盘作为该 `call_id` **执行闭环**依据；无则实时路径 **重授权并重执行**。  
- **风险承认**：若「远端已执行、结束事件丢失」，**重执行**可能重复副作用；该风险由产品侧接受。  
- **缓解建议**：通过工具幂等、远端幂等键、补偿流程降低风险。

### 5.5 状态真相：锚点事件与过程信号

**Core replay** 为继续推理组上下文时，**有效输入**侧重：**用户消息、助手文本、工具请求、`RequestsDone`、执行结束事件（`ToolCallFinished`）、`InvokeFinished`** 等。  
**过程 / 观测类**：`AssistantToolCallAuthorizationRequired`、`ToolCallAuthorization`、`ToolCallStarted`——**不**把工具结果写入发回模型的消息；其重复不改变由结束事件主导的恢复结论。  
`**call_id`** 及请求中的 name/arguments 用于区分同批并行调用。  
**Session** 为流程状态权威，**Agent** 为执行引擎，**UI** 为投影。

### 5.6 事件模型：`ToolCallStarted` 与 `ToolCallFinished`

**背景**：`ToolCallAuthorization`（允许）≠ 工具调用已在执行；中间存在调度与 await 间隙。`**ToolCallStarted`** 用于实时 UI、指标与 transcript 区分「执行前 / 执行中」。历史只读 UI 若已过滤授权类事件，对 `**ToolCallStarted**` 是否展示由产品另定（与授权类过滤规则可独立）。

**决策（规范）**

1. `**ToolCallStarted { call_id }`**：为本事件族 **正式成员**；在实现中 **固定唯一挂点**（例如紧挨 `Toolbox::call_tool` 的 `await` 前后之一），并在实现/接口文档中写明；用户 **拒绝** 授权时 **不** 发送本事件。
2. `**ToolCallFinished`**：由 `**ToolResult**` **更名**而来，载荷保持 `**call_id` + `content`**（及适用时的错误/拒绝语义）。**闭环判定**仅依据 `**ToolCallFinished`**，**不**依据 `ToolCallStarted`；仅有 Started、无 Finished = **未闭环**。
3. **与 core replay**：`ToolCallStarted` **不** 产生发回模型的 `Tool` 消息内容（与授权类过程事件类似）；**恢复锚点**仍以 `**ToolCallFinished`** 等为主，**§5.5** 不变。

**迁移与落地**：serde、JSONL transcript、replay、spec、demo 须提供兼容或一次性迁移路径。推荐顺序：锁定 `**ToolCallStarted`** 挂点并实现外抛 → 完成 `**ToolResult` → `ToolCallFinished**` 重命名与 **旧 transcript 事件**兼容 → 同步 UI 与消费者。

### 5.7 场景澄清：新用户输入与未闭合工具批次的关系

本节讨论的是 **transcript 中的事件序列语义**，不是“运行中并发调用 API”。

- **前提**：core API 语义上，`Session::resume` 与 `Session::run` 都是单条事件流消费；本 ADR 不讨论“`resume` 未完成时并发发起 `run`”的并发控制。
- **本节场景**：在**已持久化 transcript** 中出现「某轮工具批次尚未结束，随后又出现新的用户输入」的序列。
- **当前约束**：该序列应被视为“上一轮被后续用户输入打断后 **transcript** 所记录的事实”；是否丢弃未闭合批次、合成闭合或标记重跑，属于 replay 策略定义，不等同于运行期并发问题。

## 6. 影响与非目标

**积极影响**：可验证的恢复边界、复杂度可控、副作用策略可讨论；与当前 session-centric 实现一致。  
**代价**：无法承诺严格 token 级连续体验；工具需 **能力分级**（只读 / 幂等 / 非幂等）。

**非目标**（本 ADR 不承诺）：

- 任意中断点的字节级一致续写  
- 对所有第三方工具统一幂等重放  
- UI 与 Agent **双主**强一致叙事

---

## 7. 实施与后续事项

- 最小闭环：全量 transcript；历史 UI 对授权类事件统一过滤；实时与 transcript 共用 `AgentRunResponseMessage`（及 `UserMessage` 行）。  
- 「结果不明调用」处置流程（保守路径与产品简化路径）。  
- 工具能力标签与恢复/重试策略映射。  
- 按阶段与 **§2.3 / §5.2** 场景搭建恢复测试矩阵。  
- 落实 `**ToolCallStarted`** 与 `**ToolCallFinished**`（原 `ToolResult`）的实现、serde/旧 **transcript** 兼容及消费者更新。  
- 合成事件（`RequestsDone`、助手文本结束等）落盘与追溯字段约定。
